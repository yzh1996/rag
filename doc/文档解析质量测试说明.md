# 文档解析质量测试说明

本次增加的是**测试评估工具**。它会比较“LangChain 原生解析”和“项目现有增强流程”，没有修改正式上传流程，也没有自动修复报告中发现的问题。

## 1. 文件在哪里

| 内容 | 位置 |
| --- | --- |
| 25 份分类测试资料及标准答案 | `tests/测试资源/文档解析质量/` |
| 批量原生 / 增强对照测试类 | `tests/文档解析质量测试.py` → `TestDocumentParsingQuality` |
| 右键运行单个场景并自动打开报告 | `tests/文档解析单项测试.py` → `TestDocumentParsingByScenario` |
| 检查和报告工具 | `tests/parsing_quality_support.py` |
| 原件预览工具 | `tests/parsing_quality_preview.py` |
| 检查工具、单项入口和配置读取的测试 | `tests/test_parsing_quality_evaluator.py`、`tests/test_parsing_quality_scenarios.py`、`tests/test_settings_env_path.py` |
| 资料生成脚本 | `scripts/generate_parsing_quality_fixtures.py`、`scripts/generate_parsing_quality_excel.mjs` |
| 最近一次报告入口 | `tests/测试产物/文档解析质量/latest.html` |

原来的 `tests/文档清洗测试.py` 保持原样，仍输出原来的清洗对比产物。**运行新增的测试类，才会生成这里说明的新报告。**

## 2. 怎样运行

### 推荐：在 IDE 中右键运行单个场景

1. 打开 `tests/文档解析单项测试.py`，选择项目的 `.venv` Python 解释器。此单项入口同时支持 **unittest 和 pytest**，PyCharm 当前若使用 unittest，可以继续使用。
2. 找到想看的中文方法，例如 `test_模拟盖章扫描件`、`test_双栏阅读顺序`、`test_Excel多工作表与合并单元格`。
3. 在该方法上右键，选择运行。只处理这个场景，同时生成原始资料、LangChain 原生结果、项目增强结果三栏对照；结束后自动用默认浏览器打开。

共有 25 个明确命名的方法，覆盖全部现有场景。一次运行整个类或多个方法时，结果合并到同一份报告，最后只自动打开一次。扫描件沿用本机已配置的 OCR 开关；只运行选中的场景，不会顺带识别其他测试资料。

质量检查失败也会打开报告：**先保存两条路线的结果，再判断是否合格**。原生结果失败不会阻止项目增强结果生成。浏览器打不开时，控制台会提示报告的绝对路径，可以手动打开；主动强制结束进程则无法保证执行自动打开动作。

也可以用终端单独运行，例如：

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/文档解析单项测试.py::TestDocumentParsingByScenario::test_模拟盖章扫描件" -v -s --tb=short
```

`-s` 会直接显示报告路径。扫描件的原生路线不执行 OCR，可能判为失败；这表示该路线的解析质量没有达到标准，不表示报告没有生成。未开启 OCR 时，增强路线仍标记“未执行”，不会冒充质量通过。

使用 unittest 时，可以在项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -m unittest "tests.文档解析单项测试.TestDocumentParsingByScenario.test_文字PDF关键字段" -v
```

单项入口由测试类自己准备和收尾报告，不再依赖 pytest 传入 `scenario_report` 参数。因此 PyCharm 的 `_jb_unittest_runner.py` 也能加载这些方法；因缺少 `self`、`scenario_report` 而启动失败的问题已修复。该兼容调整只针对新增的单项入口，下面的批量入口仍使用 pytest。

### 保留：批量运行或只选择一条解析路线

在项目根目录用 PowerShell 执行：

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/文档解析质量测试.py" -v --tb=short
```

一份资料会分别运行 `test_native_langchain`（原生）和 `test_project_enhanced`（增强）。全部执行后有 50 个测试项。

只看原生解析：

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/文档解析质量测试.py" -k native_langchain -v
```

只测一个场景，例如普通表格：

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/文档解析质量测试.py" -k table_bordered -v
```

每次运行保存到独立的时间目录，并更新 `latest.html`。先保存报告、再判断测试是否通过，所以普通断言失败也能查看报告。若主动中断进程或使用 `-x` 提前退出，只保留已完成项；未运行的资料不会计入统计。测试文件采用中文名称，需要显式指定，不会被普通 `pytest` 自动收集。

**这些测试可能失败。** 这是严格质量评估：例如要求保留合并单元格归属，但当前解析器丢了归属，就应失败，不能为了通过而删掉标准。原生解析不支持 OCR，扫描件的文字准确性检查也会失败，报告会说明能力限制。项目自定义的页数和解压限制在原生路线标为“不适用”。

## 3. 分类资料包含什么

所有业务数据均为虚构；文件与旁边的 `golden.json` 一一对应。

| 类别 | 样例 | 重点检查 |
| --- | --- | --- |
| 文字准确性（5 份） | 文字 PDF；清晰、低清、倾斜、模拟盖章扫描件 | `0` 与 `O`、`PO-2026-000108`、`-1000.05`、日期、欧阳明、不予报销 |
| 完整性（2 份） | 文字页与扫描页混合；同一页文字加图片 | 普通页面不能丢；已有正文时仍要关注图片中的关键信息 |
| 阅读顺序（3 份） | 双栏交错存储、侧栏脚注、跨页段落 | 顺序是否符合预设阅读规则，正文是否被插入说明打断 |
| 表格关系（6 份） | 有边框、无边框、合并单元格、跨页表格、基础 Excel、多工作表 Excel | 表头、行列和金额一一对应；前导零、工作表来源、合并归属 |
| 结构来源（2 份） | 制度版本与来源 PDF、Word 标题层级 | 版本、生效日期、来源页码、标题层级；用户提供的部门等信息 |
| 清洗与异常（7 份） | Word 噪声、重复页眉页脚、中间空白页、损坏 PDF、加密 PDF、页数超限、Office 解压限制 | 噪声去除而正文保留；空白页不影响真实页码；异常文件被拒绝 |

扫描 PDF 确实由图片构成，不带隐藏文字层。低清、倾斜、盖章是在清晰样例基础上人为施加的难度，不代表真实 OCR 的准确率。

资源保护使用小文件加临时限制：例如 4 页 PDF 配合“最多 3 页”，普通 Word 配合“ZIP 条目上限 1”。不生成巨型文件或危险压缩包；测试退出后限制恢复。它验证保护机制，不代表生产大文件吞吐、内存、队列、重试或超时性能已测过。

## 4. 原生和增强有什么区别

| 路线 | 实际执行 |
| --- | --- |
| LangChain 原生 | 直接使用 `PyMuPDFLoader` / `PDFPlumberLoader` / `Docx2txtLoader` / `UnstructuredExcelLoader`，不经过项目包装 |
| 项目增强 | 项目文件安全检查 → 相同底层加载器 → PDF 扫描页检测、表格转换等现有增强 → 可选真实 OCR → 当前文档清洗 |

Excel 两条路线都保持当前默认的 `single` 模式，不能在基线中偷偷改为 `elements` 模式以改善结果。PDF 表格样例两边均使用 PDFPlumber；其他 PDF 均使用 PyMuPDF。

增强路线记录本次清洗开关、重复页眉清洗开关和相关限制。没有强行打开所有优化，因此报告体现当前项目配置。解析后未做分块，避免将分块效果和解析效果混在一起。

用户提供的部门、密级、知识库信息是上传信息，不是解析器从文档中“猜出来”的。原生路线不要求具备项目注入能力。PDF 原生页码常从 0 开始，比较时换算为从 1 开始，原始记录保留原值。

## 5. 报告怎样判断质量

每份资料有独立标准答案，先按样例设计写好，再去解析文件，不会拿解析结果当答案。

- **关键字段**：检查数字、符号、姓名、否定词。只容忍空白差异，不把 `O` 替换成 `0`，不丢负号或小数点。
- **字符错误率**：文字参考 PDF 额外计算错字、漏字、多字占标准字数的比例，只忽略空白。它只适用于这一份完整参考文本，不能据此宣称所有文档准确率。
- **阅读顺序**：按独立标记检查先后关系；标记缺失或顺序错都会失败。
- **表格关系**：检查输出中的 Markdown 或 HTML 表格行，不能把“所有词都出现了”当成行列正确。合并单元格不得丢归属；不会回读原始文件为输出补答案。
- **结构与来源**：检查页码、来源、工作表名、Word 标题层级等。
- **清洗和异常**：检查噪声是否清除、正文是否保留、异常文件是否按预期拒绝。

报告分别呈现“解析正常返回/抛出异常”和“质量通过/不通过”。拒绝加密文件属于保护检查通过；解析正常返回但金额错误属于质量不通过。

当前字段检查保持精确匹配：中文冒号 `：` 变成英文冒号 `:` 也会导致失败。这类符号差异不等于金额或编号的值一定错了，需要对照全文判断；本次开启 OCR 和增加原件展示，没有改变已有评分标准。真实识别中也出现了 `OOO` 被读为 `000`、低清样例 `PO` 被读为 `P0` 的内容错误。

报告有四种状态：通过、不通过、未执行、不适用。存在任何失败项时整体为“不通过”；无失败但仍有 OCR 项未运行时为“未执行”，不能当成通过。部分子项仍可独立通过。

HTML 现在按三栏展示：**原始资料与标准答案 → LangChain 原生结果 → 项目增强结果**。两种解析结果的全文默认展开，还能逐项查看标准和实际内容。

原始资料栏展示 PDF 各页原图（点击可放大）、Word 段落和标题样式、Excel 工作表和合并单元格，并提供原件副本和标准答案。Word、Excel 展示的是结构预览，不保证与 Office 的分页、字体、列宽完全相同。原件预览不调用 OCR，也不为两种解析结果补文字或参与评分；损坏和加密 PDF 无法预览时会直接说明。

报告目录内保存原件副本、标准答案副本、PDF 页图，便于对照。JSON 额外保留每个输出单元的元数据、项目清洗前的解析结果、OCR 检测页和实际完成页。时间目录中的每个案例还保存 `native.txt/json`、`project.txt/json`。报告不保存 OCR 凭据。

## 6. 怎样测真实 OCR

真实 OCR 由 `PARSING_QUALITY_RUN_OCR` 明确控制：默认关闭；可在项目根目录的本机 `.env` 中保存 `PARSING_QUALITY_RUN_OCR=1`，之后从终端或 IDE 直接运行测试都会使用这个选择。终端同名环境变量优先，例如设为 `0` 可临时关闭。

配置文件现已固定定位到项目根目录的 `.env`，从项目根目录或 `tests` 目录启动都会读取同一份配置，系统环境变量仍然优先。此前使用相对位置查找配置，从 `tests` 启动时会漏读根目录的 OCR 开关及凭证，导致扫描件报告显示“未执行真实 OCR”。修改后需要重新运行测试生成新报告，已有报告保留当时的实际结果。

本机本次已按用户确认开启，并配置了腾讯 OCR。凭据保存在被 Git 忽略的 `.env`，使用项目要求的 `TENCENT_OCR_SECRET_ID`、`TENCENT_OCR_SECRET_KEY` 名称；用户提供的 `TENCENTCLOUD_SECRET_ID/KEY` 已按这两个名称保存，项目代码没有包含真实密钥。原生路线始终不执行 OCR。

临时强制开启的运行方式：

```powershell
$env:PARSING_QUALITY_RUN_OCR = "1"
try {
    .\.venv\Scripts\python.exe -m pytest "tests/文档解析质量测试.py" -v --tb=short
} finally {
    Remove-Item Env:PARSING_QUALITY_RUN_OCR -ErrorAction SilentlyContinue
}
```

临时关闭真实 OCR：

```powershell
$env:PARSING_QUALITY_RUN_OCR = "0"
try {
    .\.venv\Scripts\python.exe -m pytest "tests/文档解析质量测试.py" -v --tb=short
} finally {
    Remove-Item Env:PARSING_QUALITY_RUN_OCR -ErrorAction SilentlyContinue
}
```

使用项目现有的 `OCR_PROVIDER`，调用云 OCR 会产生费用。测试不会自动安装 OCR 或创建凭据。真实 OCR 失败也会保存原因，不能通过模拟识别结果声称准确率合格。开启开关不代表每页都做 OCR：只有项目当前检测到的扫描页会调用服务，同页混合图文的漏检问题仍会如实报出。

## 7. 正式上传现在怎样把关

当前正式流程已有：格式和大小检查、Office 解压限制、PDF 页数/加密检查、OCR 异常和空结果检查、清洗后非空检查、内容/切片预览与确认、向量写入数量检查。

但“解析成功”主要表示程序没有抛异常、产出可用内容。它**不能证明金额正确、双栏顺序正确、表格关系正确**。腾讯 OCR 当前也没有把服务返回的置信度用于质量放行。这次新增报告只用于离线资料评估，还没有接入每次上传的自动放行流程。

后续真实业务资料仍需要人工抽样：这些合成样例不是行业基准，也没覆盖手写、任意扫描噪声、所有模板或真正的跨页表格连续对象重建。

## 8. 维护样例与工具

已有资料可以直接测试，无需重新生成。新增样例时，先独立定义标准答案，再生成文件并检查版面。

生成脚本需要当前项目的 PDF、Word、图片依赖，以及已安装 `@oai/artifact-tool` 的 Node 环境：

```powershell
.\.venv\Scripts\python.exe scripts/generate_parsing_quality_fixtures.py --node node
```

如果使用独立的 Node 依赖目录，可将 `ARTIFACT_NODE_MODULES` 指向该环境的 `node_modules`；中文字体默认使用 Windows 微软雅黑，可通过 `PARSING_FIXTURE_FONT` 指定其他中文字体。生成脚本不调用 OCR 或大模型。

工具自身的回归测试：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_parsing_quality_evaluator.py tests/test_parsing_quality_scenarios.py tests/test_settings_env_path.py -q
```

它用人为构造的 `0/O` 错误、丢负号、丢小数点、否定词缺失、顺序颠倒、表格错配来验证检查工具，也验证未开 OCR 不会调用外部识别、失败前保存两条路线、单项方法覆盖全部资料、多个场景只打开一次报告、浏览器不可用时保留路径等行为。还会在独立进程中分别使用 unittest 和 pytest，核对通过、失败、跳过和报告收尾行为。这些工具测试不会调用云 OCR，也不会真的打开浏览器。

配置回归测试使用临时项目和虚构凭证，验证根目录与 `tests` 目录的读取结果一致、启动目录的其他 `.env` 不会误覆盖项目配置，以及系统环境变量仍可覆盖 OCR 开关和凭证。

本次已渲染检查 PDF、扫描件和 Excel 预览。Word 已核对文本、样式、页眉和 ZIP 结构；由于本机缺少 LibreOffice，尚未完成 Word 的页面渲染复核。
